# Первый запуск Maths4U на Hostinger Business

Целевой адрес: `https://arena.maths4u.sbs`. Репозиторий: `albert123-arch/maths4u-arena`, ветка развёртывания: **`hostinger-preview`**. `main` и его автоматическое развёртывание не переключать. Папки, сайты и базы проектов `AS&A level maths` и `olymp` не используются.

Этот документ описывает подготовленную конфигурацию. Он не подтверждает выполненный деплой, доступ к удалённой MySQL, действующие настройки hPanel или постоянство файлов на сервере. Результат Linux-проверки смотрите в GitHub Actions для конкретного отправленного коммита; локальные проверки описаны отдельно в [VERIFICATION.md](VERIFICATION.md).

## Настройки hPanel

Hostinger Business поддерживает серверные Node.js-приложения. npm выполняется системой развёртывания, но недоступен через SSH. Вручную выбирается framework **Other**, позволяющий задать Output directory и Entry file. Это необходимо для стартового файла, который сначала готовит базу и затем запускает Next.js. [Официальная инструкция Hostinger](https://www.hostinger.com/support/how-to-deploy-a-nodejs-website-in-hostinger/).

В настройках Node.js Web App для Arena задайте:

| Поле | Значение |
| --- | --- |
| Repository | `albert123-arch/maths4u-arena` |
| Branch | `hostinger-preview` |
| Framework preset | `Other` |
| Root directory | `.` — корень репозитория с `package.json` |
| Node.js | `22.x`, версия не ниже `22.12.0` и ниже `23` |
| Package manager | `npm` |
| Build command | `npm run build:hostinger` (при выборе имени script — `build:hostinger`) |
| Output directory | `dist` |
| Entry file | `server.js` |
| Start command, если такое поле есть | `node server.js` либо `npm start` |
| Domain | `arena.maths4u.sbs` |

Команды build/start задаются в hPanel для его runner. Их не нужно выполнять через SSH. Репозиторий включает `.npmrc` с `include=dev`: TypeScript, Tailwind и esbuild нужны даже при `NODE_ENV=production` на этапе сборки. В итоговый `dist` отдельная команда явно устанавливает только production-зависимости. Если интерфейс предлагает только ограниченный список команд, выберите script `build:hostinger` из `package.json`.

В `dist/server.js` находится полный стартовый сценарий. Если Hostinger разрешает Entry file относительно исходного корня, корневой `server.js` при `MATHS4U_ENV=production` передаёт управление `dist/server.js`. Если Entry file разрешается внутри Output directory, используется непосредственно `dist/server.js`. Не задавайте `next start` или `next-server.cjs`: они пропускают подготовку runtime. Точное поведение полей конкретной панели необходимо подтвердить первым запуском и его runtime log. Hostinger документирует настройку entry из start-script и автоматическую установку зависимостей, сборку и запуск. [Build и entry](https://www.hostinger.com/tutorials/deploy-node-js-application).

Приложение читает `PORT`, предоставленный хостингом, и слушает `0.0.0.0`. Если `PORT` не задан, используется `3000`; не подставляйте публичные порты 80/443. Hostinger указывает 3000 в своей диагностике. [Проверка параметров](https://www.hostinger.com/support/fix-failed-to-build-application-error-hostinger-node-js/).

## Переменные приложения

Вводите секретные значения только в приватные поля Environment Variables hPanel. Не переносите старый `.env`, весь файл с внешними секретами или локальную тестовую конфигурацию. Переменные hPanel не записываются в GitHub. [Настройка переменных](https://www.hostinger.com/support/how-to-add-environment-variables-during-node-js-application-deployment/).

| Переменная | Настройка |
| --- | --- |
| `MATHS4U_ENV` | `production` — явное разрешение production |
| `NODE_ENV` | `production` |
| `APP_URL` | `https://arena.maths4u.sbs` — без завершающего `/` |
| `MATHS4U_DATABASE_URL` | Приватный URL только новой базы; пароль в URL должен быть percent-encoded |
| `MATHS4U_DATABASE_NAME` | Точное имя этой базы из hPanel, включая префикс аккаунта; должно совпадать с URL |
| `PRIVATE_STORAGE_PATH` | Реальный абсолютный путь, определённый на сервере по инструкции ниже |
| `MATHS4U_RUN_MIGRATIONS` | `1` — применять существующие миграции на каждом запуске; уже применённые не повторяются |

Для первоначального создания администратора дополнительно задайте приватные `NEW_ADMIN_USERNAME`, `NEW_ADMIN_PASSWORD`, `NEW_ADMIN_NAME` и переключатель `MATHS4U_BOOTSTRAP_ADMIN=1`. Логин: 3–64 символа `a-z`, цифры, `_`, `.` или `-`. Пароль: минимум 10 символов, максимум 72 байта UTF-8. Значения учётных данных не помещайте в команды, логи, README или чат.

После первого успешного входа администратора удалите из hPanel четыре временные переменные: `MATHS4U_BOOTSTRAP_ADMIN`, `NEW_ADMIN_USERNAME`, `NEW_ADMIN_PASSWORD`, `NEW_ADMIN_NAME`. Затем перезапустите или повторно разверните приложение. `MATHS4U_RUN_MIGRATIONS=1` оставьте для следующих релизов. Значение `0` поддерживается только как режим проверки: приложение запустится, если все миграции данной сборки уже успешно применены, их контрольные суммы совпадают и незавершённых миграций нет. При необходимости новой миграции запуск остановится.

`MATHS4U_BUILD` — внутренний флаг скрипта сборки; **не добавляйте его в hPanel**. `DATABASE_URL` и `DB_*` игнорируются. Без явного `MATHS4U_ENV=production` сохраняется ограничение на loopback-базы `maths4u_dev*` / `maths4u_test*`. Production-конфигурация не подхватывает старые реквизиты автоматически.

## База, миграции и первый администратор

В hPanel → нужный сайт → Databases → Management определите **новую пустую базу Arena**, назначенного ей пользователя, хост и порт. Не считайте `localhost` гарантированным значением: используйте сведения данного аккаунта. MySQL URL должен иметь схему `mysql://`; произвольные параметры URL/TLS сейчас не поддерживаются. Hostinger допускает создание таблиц программно из приложения или через phpMyAdmin, но не гарантирует доступ к MySQL из build-среды. [Официальная инструкция MySQL](https://www.hostinger.com/support/connecting-a-hostinger-mysql-database-to-a-node-js-application/).

Подготовленный порядок не зависит от подключения к MySQL при сборке:

1. Runner выполняет `build:hostinger`: Prisma Client → Next.js → самодостаточный `dist`. Доступ приложения к БД блокируется внутренним флагом сборки; реквизиты БД и первого администратора не нужны дочерним build-процессам.
2. В `dist` входят существующая схема и миграции, production-зависимости, Prisma CLI и native schema-engine текущей платформы. Engine устанавливается и проверяется на этапе сборки, его путь фиксируется в manifest. На runtime не выполняется npm install и не скачивается engine.
3. `server.js` проверяет production-конфигурацию, платформу сборки, порт и приватное хранилище. Затем подключается к явно указанной БД и получает MySQL advisory lock для подготовки этой базы.
4. Допускается пустая база либо журнал миграций этой версии Maths4U с известными именами и контрольными суммами. Чужой журнал, неизвестные изменения и непустая база без подходящего журнала останавливают запуск. Скрипт не исправляет такие случаи сбросом данных.
5. Выполняется штатный `prisma migrate deploy` через текущий Node-процесс и упакованный CLI/engine. `migrate dev`, `db push`, reset, seed и тестовые импорты не запускаются. Повторный запуск сохраняет данные.
6. Первый администратор создаётся в транзакции, только если его ещё нет и включён bootstrap. Существующий администратор сохраняется целиком, включая пароль и роли. Совпадение желаемого логина с уже зарегистрированным пользователем останавливает создание, а не повышает его роль. В БД остаётся одноразовая отметка bootstrap: удаление всех ролей ADMIN не разрешает повторное автоматическое создание.
7. Временные учётные переменные удаляются из окружения процесса; блокировки освобождаются; запускается Next.js и открывается HTTP-порт.

Публичного API для миграций или выдачи роли администратора нет. Если миграция завершилась ошибкой, в runtime log выводится этап и, при наличии, код Prisma без реквизитов. Исправление частично выполненной миграции требует отдельного анализа; повторный запуск не делает reset. Не запускайте подготовку на базах двух старых проектов.

## Постоянные приватные файлы

Hostinger управляет `hbuilds` и `public_html`, перезаписывая их при деплоях; версия приложения выбирается через `hbuilds/current`. Приватные загрузки должны храниться отдельно от этих деревьев и каталога сборки. [Структура развёртывания Hostinger](https://www.hostinger.com/support/how-to-deploy-a-nodejs-website-in-hostinger/).

Абсолютный путь зависит от аккаунта и устройства конкретного сайта. Не копируйте вымышленный путь вида `/home/...` из примера. Определите его так:

1. Откройте File Manager именно сайта Arena и найдите его действительный каталог домена, содержащий управляемые папки. Нужен отдельный каталог приватных данных, доступный процессу Arena. Не используйте каталоги других сайтов. File Manager поддерживает навигацию и настройку прав. [File Manager](https://www.hostinger.com/support/4548688-basic-actions-in-the-file-manager-in-hostinger/).
2. Через SSH перейдите в **подтверждённый каталог Arena вне `hbuilds` и `public_html`**. Проверьте `pwd -P`. Для первого создания отдельной папки выполните `mkdir -m 700 -- maths4u-private`, затем `realpath -- maths4u-private`. Это обычные файловые команды, Node/npm через SSH не нужны. Если каталог домена сам находится внутри `public_html` либо доступ наружу запрещён, запросите у поддержки Hostinger доступный постоянный приватный путь для этого Node.js-приложения.
3. Полученный абсолютный путь внесите в `PRIVATE_STORAGE_PATH`. Если SSH/`realpath` недоступны и панель показывает только относительный путь, полный путь и доступ процесса уточните у поддержки; не угадывайте его. Не устанавливайте права `777`.
4. При старте приложение разрешает symlink через realpath и отклоняет путь внутри `hbuilds`, `public_html` или собственного каталога приложения. Оно проверяет создание/чтение файла. В runtime log появляется `Storage probe created` либо `Storage probe preserved` и SHA256 контрольного файла.

Запись при первом старте ещё не доказывает сохранность после деплоя. Для проверки:

1. После входа обычным интерфейсом загрузите небольшой PDF в приватную работу. Скачайте его с авторизацией и сохраните локальный SHA256, например через `Get-FileHash -Algorithm SHA256` в PowerShell. Запишите SHA256 storage probe из runtime log.
2. Повторно разверните **тот же commit** ветки `hostinger-preview`, сохранив `PRIVATE_STORAGE_PATH`. В журнале ожидается `Storage probe preserved` с прежним SHA256.
3. Снова скачайте то же вложение тем же пользователем и сравните SHA256/байты. Откройте ссылку на этот приватный файл без авторизации: содержимое не должно выдаваться; ожидается отказ 401/403 либо 404.
4. Подтвердите сохранность записей БД и неизменность первого администратора. Только после этих проверок можно считать хранение между реальными деплоями проверенным. Резервируйте MySQL и приватный каталог вместе.

## Проверки выпуска и недостающие данные hPanel

Локально или в CI используются `npm run build:hostinger`, `npm run verify:hostinger`, `npm run test:hostinger`. GitHub Actions для preview собирает пакет на Linux/Node.js 22, использует отдельную тестовую MySQL и проверяет повторный запуск, сохранность администратора/файлов и переданный `PORT`. Это не проверка сервера Hostinger. Не загружайте Windows-каталог `dist`: отправляйте исходники, чтобы Linux-зависимости собирал runner. Итоговый пакет проверяется на отсутствие локальных `.env`, `.local`, application fixtures, тестовых данных и обнаруженных секретов.

Для следующего шага нужны:

- Карточка Node.js Web App **именно Arena**, её текущая ветка и наличие полей Other/root/build/output/entry; выбранная ветка должна быть `hostinger-preview`.
- Подтверждение новой пустой БД и назначенного ей пользователя; её хост/порт. Значения URL, имени БД и пароля вводятся приватно в hPanel.
- Проверенный абсолютный `PRIVATE_STORAGE_PATH` и доступ процесса приложения к нему.
- Заполненные приватные переменные первого администратора.
- Связь `arena.maths4u.sbs` с этим приложением и готовый HTTPS. Если потребуется DNS, изменяется только настройка целевого поддомена.

Не удаляйте существующие сайты для выполнения этой инструкции и не переключайте `main`. При выборе другой ветки проверяйте настройки до запуска redeploy: Hostinger использует последнюю версию выбранной ветки. [Повторное развёртывание](https://www.hostinger.com/support/how-to-redeploy-a-node-js-application/).

После первого запуска проверьте runtime log, `/api/health`, вход администратора, регистрацию ученика и загрузку приватного файла на целевом HTTPS-адресе. `/api/health` подтверждает доступность приложения и его БД, но не заменяет проверку прав и постоянства файлов. Журналы runtime и build рассматриваются отдельно. [Runtime logs](https://www.hostinger.com/support/how-to-use-node-js-runtime-logs-at-hostinger/).
